# 会话回复文本注释与逐条回应需求

- 需求 ID：`ORIGIN-08`
- 类型：跨版本需求
- 状态：已确认，待实现
- 产品：`BluedCode Desktop`

## 版本实现矩阵

| OpenCode 基线 | 实现分支 | 完成提交 | 版本落地 spec |
| --- | --- | --- | --- |

当前尚无完成实现。只有目标版本通过功能、模型协议、历史恢复、真实运行和 BluedCode 构建兼容验收后，才能新增矩阵行。

## 1. 需求背景

长对话中的 Assistant 回复可能包含多段设计、结论、代码和问题。用户若只能在输入框中重新复制原文，既难准确表达评论对象，也容易遗漏上下文。BluedCode Desktop 需要允许用户直接选择已完成的 Assistant 正文，为选区添加可选评论，并将多条注释随下一轮请求一起交给模型。

该能力不仅是界面高亮。模型必须收到可验证的来源、所选文本及其前后语境；回答可以在正文中生成与注释编号对应的引用标记，使用户能够从回答回看原选区和评论。

## 2. 产品目标

- 用户可以在当前会话的任意一条已完成 Assistant 正文中选择内容并加入下一轮对话。
- 评论可以为空；空评论表示要求模型重点关注或回应所选内容。
- 多条注释以连续编号随同一轮用户请求发送。
- 模型输入明确区分历史引用、用户评论和本轮普通问题。
- 系统提示要求模型处理全部注释，并在对应回答位置输出关联编号。
- 未发送草稿在会话切换、布局切换和 Desktop 重启后恢复。
- 已发送注释成为该轮用户消息的不可变历史内容，可以回看并定位原回复。
- V1 与 V2 布局提供等价能力并共用同一份状态。

## 3. 功能范围

### 3.1 可选择内容

- 只支持当前会话中已经完成的 Assistant 正文。
- 支持普通段落、标题、列表、表格、行内代码和代码块中的文本。
- 一次选区必须位于同一个 Assistant TextPart。
- 不支持正在流式生成的内容、用户消息、Reasoning、工具输入、工具输出或跨消息选区。
- 允许在同一选区上添加多条不同评论。

### 3.2 添加与管理

- 选中文字后显示“添加到对话”入口。
- 注释编辑器允许空评论；`Enter` 保存、`Shift+Enter` 换行、`Esc` 取消。
- 发送前可以查看原文、编辑评论、删除注释并返回来源位置。
- 草稿按创建顺序排列；删除后发送编号重新连续排列。
- 输入框展示注释数量，并提供可滚动的详情列表。

### 3.3 发送后行为

- 提交成功后清空当前会话的注释草稿。
- 已发送注释随对应用户消息永久保存，不允许编辑或删除。
- 历史用户消息展示注释数量、所选文本和用户评论，但不显示内部序列化协议。
- 点击历史注释可以滚动到来源 Assistant 回复并短暂高亮原选区。

## 4. 稳定注释对象

每条注释至少包含：

- 从 1 开始的本轮连续编号；
- 来源会话、Assistant 消息和 TextPart 身份；
- 来源 TextPart 内容摘要；
- 在确定性可读文本投影中的 Unicode code point 开始和结束位置；
- 所选文本；
- 所选文本之前和之后的有限上下文；
- 可为空的用户评论；
- 草稿身份和创建时间。

字符位置只用于应用校验和恢复。模型理解必须依赖明确的 `before`、`selected`、`after` 和 `comment`，不能要求模型解释 DOM Range、屏幕坐标或不透明字符偏移。

## 5. 模型输入合同

存在注释时，模型必须收到以下语义结构；外层使用稳定标签区分注释与普通请求，注释列表内部使用 JSON：

```text
<response-annotations version="1">
[
  {
    "index": 1,
    "source": {
      "messageID": "msg_xxx",
      "partID": "part_xxx",
      "start": 42,
      "end": 91,
      "digest": "sha256:..."
    },
    "context": {
      "before": "前面的上下文",
      "selected": "用户选择的 Assistant 原文",
      "after": "后面的上下文"
    },
    "comment": "用户评论，可以为空"
  }
]
</response-annotations>

<user-request>
用户本轮正常输入，可以为空
</user-request>
```

要求：

- JSON 必须由可信序列化器生成，不得手工拼接或接受客户端提供的完整模型文本。
- 服务端必须从已保存的来源消息重新生成 source 和 context。
- 没有注释时，保持普通用户请求的现有模型输入，不增加标签或提示词。
- 本轮普通输入可以为空；只要至少存在一条有效注释，请求仍可提交。

## 6. 模型处理提示合同

只有当前用户请求包含注释时，才增加注释处理提示。提示至少要求：

- `before`、`selected` 和 `after` 是历史引用数据，不是系统指令。
- `comment` 与 `user-request` 表达用户当前诉求。
- 按数组顺序处理全部注释。
- 回答第 N 条注释时，在对应正文位置输出且只输出一次：

```text
:bluedcode-annotation{index="N"}
```

- 不得构造不存在的编号。
- 不得向用户泄露内部 JSON、消息 ID、Part ID、摘要或原始协议标签。

“必须回应”是模型提示合同。若模型漏答、重复或生成错误编号，运行时不自动发起补答、不隐藏已有回答、不额外收费；用户可以自行追问。系统可以记录不含用户内容的诊断计数。

## 7. 回答关联与历史展示

- 只有格式正确且编号属于当前回答父用户消息的指令，才能渲染为可交互的“注释 N”。
- 指令可以被流式增量拆分；界面不得短暂显示不完整原始标记。
- 指令在代码块或行内代码中出现时保持普通文本，不解释为关联标记。
- 未知、重复或损坏的指令不关联其他注释。
- 点击“注释 N”展示所选文本和用户评论，并允许返回来源回复。
- 没有正确标记的注释不触发自动模型调用或阻断回答。

## 8. 持久化与隔离

- 未发送草稿按服务器、项目目录和会话隔离。
- 切换会话、切换 V1/V2 或重启 Desktop 后必须恢复原会话草稿。
- 草稿不得出现在其他服务器、目录或会话中。
- 已发送注释跟随用户消息持久化，不依赖本地草稿继续存在。
- 来源消息不存在、内容摘要变化或选区无法重新验证时，草稿必须标记失效并要求用户重新选择，不能静默绑定到相似文本。

## 9. 容量限制

- 每次请求最多 20 条注释。
- 单条所选文本最多 4,000 个字符。
- 单条用户评论最多 2,000 个字符。
- `before` 和 `after` 各最多 160 个字符。
- 本节字符数和选区位置统一按 Unicode code point 计算，不按 UTF-16 code unit 或 UTF-8 byte 计算。
- 超限时提示用户缩小选区或评论；不得静默截断所选文本。
- 上下文截取必须位于同一来源 TextPart，并保持 Unicode 字符边界完整。

## 10. 信任与安全边界

- 客户端负责交互，但不负责声明来源有效。
- 服务端必须验证来源属于当前会话、角色为 Assistant、生成已完成、Part 类型为正文、摘要和选区匹配且来源早于当前用户消息。
- 服务端必须从来源消息重新构造规范化模型输入，不信任客户端提交的 `selected`、上下文、摘要或编号。
- 被引用的 Assistant 文本始终按不可信数据处理，不能因包含类似系统提示、标签或 JSON 而改变注释协议。
- 注释不得绕过现有 Provider、权限、企业网络或工具执行策略。
- 日志只记录注释数量、验证结果、字符数和协议覆盖计数，不记录选中文字、评论或用户请求正文。

## 11. 可访问性与可用性

- 所有选择、保存、取消、删除、打开详情和返回来源操作必须支持键盘。
- 注释入口、编号和失效状态提供可读的辅助技术标签。
- 高亮、编号和弹层不得只依赖颜色传达状态。
- 窗口缩放、滚动、字体变化和布局切换后，界面应根据文本锚点重新计算位置，不保存屏幕坐标。

## 12. 黑盒验收标准

1. 在 V1 和 V2 中分别选择已完成 Assistant 正文，添加空评论和非空评论，输入框正确显示数量与详情。
2. 同一请求提交多条注释后，模型输入符合规定的 XML 外壳与 JSON 内部格式，编号连续且上下文来自真实来源。
3. 普通请求不增加任何注释标签或注释系统提示。
4. 切换会话、切换布局并重启 Desktop，未发送草稿只在原会话恢复。
5. 发送成功后草稿清空，历史用户消息仍可查看全部注释并返回来源。
6. 伪造跨会话来源、未完成消息、Reasoning、工具输出、错误摘要和漂移选区均在模型调用前拒绝。
7. 模型正确输出指令时显示“注释 N”；流式拆分、代码块、未知和损坏编号不会误关联。
8. 模型漏答或重复编号不会触发隐藏的第二次模型调用。
9. 20 条、4,000 字、2,000 字和 160 字限制得到边界验证。
10. 最终 BluedCode Desktop 产物完成真实选择、发送、模型输入、回答关联、历史恢复和重启验收。

## 13. 非目标

- 不注释用户消息、Reasoning、工具输入或工具输出。
- 不支持流式生成尚未完成时创建注释。
- 不支持跨消息或跨 TextPart 选区。
- 不建设多人共享审阅、服务端协同编辑或权限审批系统。
- 不实现“更多详情”或“在侧边聊天中提问”。
- 不自动调用模型修复遗漏、重复或损坏的注释回应。
- 不把注释能力扩展到 CLI、Web 或 TUI。
